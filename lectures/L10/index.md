## 摘要（Abstract）

一棵 [B+ 树](#B+%20树)可以在每次插入、删除结束后都满足结构要求，却仍然在并发执行时返回错误结果：查找线程刚根据[分隔键](#分隔键)选好下一条指针，另一个线程就把目标键搬到了别的叶节点。保护[索引](#索引)因此需要覆盖操作之间的衔接，尤其是“根据父节点作出决定”与“进入子节点”之间的那一小段时间。

[闩](#闩)提供短时间的读写互斥，协议则决定哪些节点需要加[闩](#闩)、何时能够放[闩](#闩)。固定布局的[哈希表](#哈希表)允许线程逐[页](#页)或逐[槽](#槽)向前探测；[B+ 树](#B+%20树)的[分裂](#分裂)、合并会改变[访问路径](#访问路径)，需要[闩蟹行协议](#闩蟹行协议／闩耦合)在父子节点间交接保护。节点能够独立承受本次变化时，祖先上的[闩](#闩)便可以释放。进一步假定多数更新不会改变树结构，就能让线程先沿[读闩](#读闩)下降，只在[叶节点](#叶节点)取得[写闩](#写闩)；假设不成立，再按较保守的协议重试。

范围扫描把访问方向从向下扩展到横向，带来了循环等待的可能。解决它需要把获取兄弟[闩](#闩)失败视为一种正常结果：结束本次尝试，清理局部修改，释放所持[闩](#闩)，再重新执行。掌握这些机制后，应当能够逐步解释一个线程为何仍需持有某个祖先的[闩](#闩)、为何可以释放另一个，以及一次等待究竟只是[冲突](#冲突)，还是已经构成[死锁](#死锁)。

## 1. 多个执行者共享一份结构，正确性就有了两层

📍 *PPT 第 4–9 页*

### 1.1 多核带来的机会，也带来了中间状态

📍 *PPT 第 4–5 页*

单线程操作一棵树时，程序可以先搬动键，再修正指针，最后更新节点中的计数。只要下一次操作开始前整理完毕，算法就能正常工作。多个线程共享这棵树后，另一个线程可能恰好在这几个动作之间开始读取，把尚未整理完的状态当成完整的树。

线程（Thread）是操作系统能够调度的一条执行流；同一进程中的线程通常共享内存，因此也能访问同一个[索引](#索引)对象。进程（Process）有相对独立的地址空间，也可以通过共享内存访问共同的数据结构。为了兼容这两种组织方式，统一把访问结构的执行者称为 **[工作者](#工作者)（Worker）**。以下例子用线程 `T1`、`T2` 表示[工作者](#工作者)。

让多个[工作者](#工作者)同时运行有两方面价值。多个 CPU 核心能够分别处理请求；一个[工作者](#工作者)等待磁盘 I/O 时，另一个还能继续计算，减少处理器空闲。若所有操作都必须等前一个操作结束，多出的核心便很难帮助这一份[索引](#索引)提高吞吐量。

也有系统选择让某个[执行引擎](#执行引擎)或某份数据结构只由一个线程访问。Redis 是材料中的代表例子。这种设计省去了该执行路径上的许多同步工作，也降低了实现难度；“数据访问单线程”不等于整个服务器只能有一个线程，网络处理等任务仍可交给其他线程。理解这种选择的关键在于：同一份可变状态是否真的会被多个执行者同时访问。
![PPT 第 4 页](slides/page-005.png)


**[并发控制协议](#并发控制协议)（Concurrency Control Protocol）**规定多个[工作者](#工作者)访问共享对象时必须遵守的规则，使允许发生的交错执行仍然满足所需的正确性。讨论协议之前，先要确定这里的“正确”指什么。

### 1.2 物理正确与逻辑正确回答不同的问题

📍 *PPT 第 5 页*

**[物理正确性](#物理正确性)（Physical Correctness）**要求数据结构的内部表示有效：键与指针保持应有的对应关系，线程不会读取一半更新完成的节点，也不会沿着失效指针访问无效内存。一次查找因为同时发生的[重分配](#重分配)而漏掉始终存在的键，也属于[索引](#索引)访问协议出了问题；[物理正确性](#物理正确性)并不只意味着“程序没有崩溃”。

**[逻辑正确性](#逻辑正确性)（Logical Correctness）**关心某个[事务](#事务)在此时应当看到哪些值，以及多个操作的结果是否符合约定的[事务](#事务)语义。[事务](#事务)（Transaction）可以先理解为应用希望作为一个整体处理的一组[数据库](#数据库)操作，完整定义将在第 [17](../L17/index.md) 讲展开。

例如，先插入键 `5`，另一个执行者随后删除 `5`，再查找 `5`。每一步都可能把 [B+ 树](#B+%20树)维护得完好，最后也确实查不到 `5`。这在结构上没有问题；应用是否应该允许看到这种结果，要结合[事务](#事务)边界和隔离规则判断。反过来，如果 `5` 从未被删除，只是在两个[叶节点](#叶节点)之间移动时被查找漏掉，就应当修复[索引](#索引)内部的访问协议。

这一区分决定了当前要保护的范围。给一个[页](#页)加上短时间的互斥保护，能够帮助读取完整的页内容；它本身并没有规定一串 SQL 语句之间的数据可见性。

### 1.3 [锁](#锁)与[闩](#闩)：保护对象和持有时间不同

📍 *PPT 第 7–9 页*

[数据库](#数据库)语境中的 **[锁](#锁)（Lock）**是保护逻辑内容的较高层机制，用来协调不同[事务](#事务)对[元组](#元组)、表等对象的访问。**[闩](#闩)（Latch）**是保护内部数据结构[临界区](#临界区)的低层同步机制。**[临界区](#临界区)（Critical Section）**就是需要受保护地访问共享状态的那段代码，例如读取一个节点的指针数组，或修改一个哈希[槽](#槽)的内容。

操作系统教材经常把后者也称为 lock。读[数据库](#数据库)论文或代码时，需要根据保护对象判断它指哪一种机制。

| 比较项 | [锁](#锁)（Lock） | [闩](#闩)（Latch） |
|---|---|---|
| 协调的执行者 | [事务](#事务) | [工作者](#工作者)、线程或进程 |
| 保护对象 | [数据库](#数据库)的逻辑内容 | 内存中的结构与[临界区](#临界区) |
| 常见持有范围 | 通常跨越[事务](#事务)中的多个操作，常持有到[事务](#事务)结束 | 一个内部操作或其一部分；内存中的短[临界区](#临界区)常以纳秒、微秒计 |
| 模式 | 共享、排他、更新、意向等模式，后续章节展开 | 这里主要使用读、写两种模式 |
| 管理方式 | 通常有锁管理器与[事务](#事务)管理机制 | [闩](#闩)状态通常放在受保护对象附近 |
| 发生等待循环时 | 系统可以检测并选择[事务](#事务)中止等措施 | 数据结构协议必须自行避免或打破这种局面 |
| 失败后的清理 | [事务](#事务)机制负责组织回滚 | 执行内部操作的[工作者](#工作者)负责恢复可用状态 |

**[读闩](#读闩)（Read Latch，R）**允许多个[工作者](#工作者)同时读取受保护对象。**[写闩](#写闩)（Write Latch，W）**允许一个[工作者](#工作者)独占对象，其他读者和写者都不能进入。

| 已持有的模式 \ 新申请的模式 | R | W |
|---|---|---|
| R | 兼容 | 不兼容 |
| W | 不兼容 | 不兼容 |

兼容表示同时持有在语义上可行，具体是否立即接纳新读者，还要看等待队列的公平策略。若一个写者已经等了很久，继续接纳读者可能让它始终没有机会运行。

这里还有一个容易误解的边界：[闩](#闩)不提供[事务](#事务)级的自动回滚服务，但受[闩](#闩)保护的操作仍可能需要撤销已经做出的修改。课件第 7 页的“不需要回滚”表述过于绝对；官方 Notes 第 2 节及课件第 38 页明确要求[工作者](#工作者)承担失败清理。第 7 节会说明这些清理如何与[写闩](#写闩)配合。

## 2. [闩](#闩)本身也有成本：怎样让保护比被保护的工作更便宜

📍 *PPT 第 10–15 页*

### 2.1 短临界区要求短的获取路径

📍 *PPT 第 10–11 页*

一次[索引](#索引)访问可能经过多个节点，每经过一个节点就申请、释放一次[闩](#闩)。如果节点上的工作只是比较几个键、读一个指针，[闩](#闩)的开销很容易超过真正的查找工作。

因此，[闩](#闩)首先需要占用很少的内存。一个[闩](#闩)多占几十字节，乘以成千上万个[页](#页)或槽位，就会挤占存放键值的空间。其次，无竞争时应当走很短的路径：既然没有别的线程阻止访问，就不应为了确认这件事而经过复杂的协调流程。

管理还应尽量分散。如果每申请一个节点的[闩](#闩)都必须访问同一张全局登记表，这张表也要被保护，结果只是把竞争转移到了新的中心。把状态放在节点或其内存管理对象附近，可以让互不相关的访问独立完成。

最后是尽量减少昂贵的系统调用。用户空间（User Space）是普通程序运行的区域，内核空间（Kernel Space）负责调度、设备等受保护功能；系统调用（System Call）让程序请求内核提供服务。进入内核、管理等待队列、切换运行线程都要付出成本。当[临界区](#临界区)很短时，为一次短暂等待走完这些流程可能得不偿失。

这些目标之间需要取舍。一直在用户空间等待可以省去睡眠和唤醒，却可能消耗本应交给其他工作的 CPU 时间。理解[闩](#闩)实现，实际是在理解“等一等”这件事可以由谁来做、付出什么代价。

### 2.2 原子操作堵住“检查完，还没修改”的空隙

📍 *PPT 第 12–13 页*

假设用变量 `M` 表示某个状态。下面的普通 C 代码表达了“值等于 20 时改成 30”的意图，却不能独自用于线程间的同步：

```c
if (M == 20) {
    M = 30;
}
```

两个线程可能都先看到 `M == 20`，随后都执行赋值。如果这个状态表示“资源尚未被占用”，两个线程就都会误以为自己取得了资源。在 C、C++ 中，对普通变量作这种无同步的并发读写还会产生数据竞争，语言本身不保证其行为。

**[原子操作](#原子操作)（Atomic Operation）**使指定操作在并发观察下不可被拆开。**[比较并交换](#比较并交换)（Compare-and-Swap，CAS）**把“比较当前位置是否等于期望值”与“相等时写入新值”合成一个原子步骤。

保留课件中的数值与接口写法：
![PPT 第 13 页](slides/page-020.png)


```c
__sync_bool_compare_and_swap(&M, 20, 30)
```

`&M` 是待访问的位置，`20` 是期望值，`30` 是新值。若比较时该位置确实为 `20`，操作把它改成 `30` 并返回成功；否则不修改它并返回失败。这是 GCC 的编译器内建接口，编译器会使用相应的原子实现；函数名中的双下划线是这一接口的命名形式，不能据此把所有双下划线函数都当成原子指令。[GCC 接口说明](https://gcc.gnu.org/onlinedocs/gcc-6.1.0/gcc/_005f_005fsync-Builtins.html)
![PPT 第 13 页](slides/page-021.png)


```text
Initial: M = 20

T1: CAS(&M, 20, 30) -> success; M = 30
T2: CAS(&M, 20, 30) -> failure; M = 30
```

两个线程不能都通过同一次状态转换取得所有权。这里原子的是这一处受支持的更新；把一整个节点中的键、计数和指针都更新正确，仍然需要更高一层的协议。

### 2.3 测试并设置自旋闩（Test-and-Set Spin Latch）

📍 *PPT 第 12–13 页*

**[测试并设置](#测试并设置)（Test-and-Set，TAS）**把标志设为已占用，并原子地返回它原来的状态。**[自旋闩](#自旋闩)（Spin Latch）**让申请者在失败后继续尝试，直到获得所有权；这段反复尝试称为自旋（Spinning）。TAS 与 CAS 都能支持这样的机制，但它们的接口语义不同：前者返回旧状态，后者比较期望值再决定是否修改。
![PPT 第 12 页](slides/page-018.png)


以下把课件的 `std::atomic_flag` 片段补齐初始化与释放，便于看清一次完整的进入和退出：

```cpp
#include <atomic>

std::atomic_flag latch = ATOMIC_FLAG_INIT;

void protected_operation() {
    while (latch.test_and_set()) {
        // Retry; a real policy may yield or back off.
    }
    // Access the protected data structure.
    latch.clear();
}
```

`std::` 表示 C++ 标准库的名字空间；`atomic_flag` 是提供原子标志操作的类型，并非普通 `bool`，也不是 `atomic<bool>` 的别名。`test_and_set()` 返回 `false`，说明原先未占用，这次调用成功取得了[闩](#闩)，因此退出循环；返回 `true` 则说明尚未取得。`clear()` 释放标志。这里使用默认内存顺序，让原子同步同时约束[临界区](#临界区)访问的可见性；实际实现还必须保证各种退出路径都正确释放[闩](#闩)。[C++ 原子标志接口说明](https://learn.microsoft.com/en-us/cpp/standard-library/atomic-flag-structure?view=msvc-170)

自旋的优势在于无竞争路径很短，也把获取失败后的选择留给了 DBMS：可以再试几次，可以让出执行机会，也可以结束本次操作尝试。若资源马上就会释放，短暂自旋可能比睡眠后再唤醒更便宜。

代价同样直接。多个等待者可能持续执行[原子操作](#原子操作)，处理器看起来很忙，[数据库](#数据库)却没有完成更多请求。操作系统只知道这些线程仍能执行指令，未必知道它们都在等同一个标志。

缓存行（Cache Line）是 CPU 缓存与内存之间传送和维护一致性的基本数据块。多个核心反复修改同一[闩](#闩)状态，会竞争其所在缓存行的所有权，产生一致性通信。**[非统一内存访问](#非统一内存访问)（Non-Uniform Memory Access，NUMA）**机器还存在不同处理器到不同内存区域的访问距离；跨插槽通信通常更贵。这里的代价不应理解为“每次循环必定读一次远端 DRAM”，但集中争抢同一状态确实会放大缓存与互连压力。

这就解释了为什么“单次原子指令很快”推不出“线程越多越快”。要衡量的是完成一次有效操作所消耗的全部工作，其中包括所有失败的尝试。

### 2.4 阻塞互斥量把等待交给操作系统

📍 *PPT 第 10、14 页*

**[互斥量](#互斥量)（Mutex）**允许一个执行者独占[临界区](#临界区)。采用阻塞等待时，拿不到[互斥量](#互斥量)的线程可以被挂起，等资源可能可用后再被唤醒。与持续自旋相比，等待者让出了处理器；相应地，系统必须保存等待状态并安排恢复执行。

课件中的接口形式是：

```cpp
std::mutex m;
// ...
m.lock();
// Do something special...
m.unlock();
```

`lock()` 取得[互斥量](#互斥量)后才返回，`unlock()` 释放它。C++ 也能用作用域管理对象自动释放：保护对象离开作用域时调用析构函数，减少因提前返回而忘记释放的问题。接口简洁并不表示底层没有工作。

Linux 中常见的实现建立在 **futex（Fast User-Space Mutex，[快速用户空间互斥机制](#快速用户空间互斥机制)）**上：无竞争时通过用户空间的原子状态完成；需要阻塞时，再借助内核的等待和唤醒机制。课件用“用户空间[闩](#闩) + OS [闩](#闩)”画出两层路径，理解时应抓住快慢路径的区别；它不意味着每次 `lock()` 都要进入内核，或应用必须依次持有两个独立的[锁](#锁)。[Linux futex 手册](https://man7.org/linux/man-pages/man7/futex.7.html)

内核安排线程睡眠，也必须保护自己的等待队列和调度数据，所以一次争用可能引出额外的同步和调度。PPT 给出的约 `25 ns` 每次 lock/unlock 调用是示例量级，不能作为所有机器上的固定成本，更不能当成一次完整睡眠、调度、唤醒的费用。
![PPT 第 14 页](slides/page-023.png)


Andy 对在很短的[数据库](#数据库)[临界区](#临界区)里频繁依赖 OS 阻塞路径持批评态度，因为 DBMS 更了解自己有哪些工作可以运行。例如，协程（Coroutine）允许程序保存一段任务的执行状态，把同一线程交给另一段任务；内部任务拿不到[闩](#闩)时，可以交回 DBMS 的调度器。若底层线程已经被 OS 挂起，这个线程上的其他任务也失去了立即运行的机会。
![PPT 第 10 页](slides/page-013.png)


从操作系统的角度，长时间自旋又是在占用核心而不做有效工作。两种立场针对的是不同等待成本：[临界区](#临界区)足够短且持有者正在运行，短暂自旋有价值；等待较长或持有者迟迟不能运行，让等待者休眠会更合理。可取的设计往往会根据等待情况切换策略。
![PPT 第 10 页](slides/page-014.png)


### 2.5 读写闩还要决定谁先运行

📍 *PPT 第 15 页*

单一模式的[互斥量](#互斥量)或[自旋闩](#自旋闩)会把所有访问排成独占访问。读者彼此不修改共享状态，通常可以一起运行，因此需要 **[读写闩](#读写闩)（Reader-Writer Latch）**：它区分读、写请求，在多个读者之间共享访问权，在写者进入时提供独占保护。

实现因此需要更多状态，例如当前读者数、是否已有写者，以及等待的读写请求。它可以在自旋原语上构建，也可以使用阻塞机制。`std::shared_mutex` 是相应的 C++ 接口例子；具体等待政策取决于实现。

考虑两个读者正在访问节点，第三个[工作者](#工作者)申请[写闩](#写闩)，第四个[工作者](#工作者)又申请[读闩](#读闩)。第三个必须等已有读者退出。第四个虽然与当前读者兼容，但若不断允许这样的后来者加入，读者数可能永远降不到零，写者也就一直无法运行。
![PPT 第 15 页](slides/page-026.png)

![PPT 第 15 页](slides/page-027.png)

![PPT 第 15 页](slides/page-028.png)


**[饥饿](#饥饿)（Starvation）**指某个[工作者](#工作者)长期得不到进展，即使系统中的其他[工作者](#工作者)仍在完成工作。读者优先倾向于继续接纳读者；写者优先会在有写者等待时限制新读者；公平策略则尝试约束插队。这些策略对吞吐量与等待时间的影响不同，不能把某一种实现中的队列行为当成所有[读写闩](#读写闩)的共同保证。

[读写闩](#读写闩)用计数和排队逻辑换取了更多共享访问机会。读多写少时，这常常值得；若把一份复杂状态复制到每个极小的键值[槽](#槽)上，空间和维护成本就可能十分显著。

### 2.6 更好的实现，仍然围绕等待方式做取舍

📍 *PPT 第 10–11 页*

**[自适应闩](#自适应闩)（Adaptive Latch）**会在短暂尝试后，按等待情况改用挂起等方式。WebKit 的 `WTF::Lock` 与 ParkingLot 展示了另一条空间优化路径：每个[锁](#锁)只保存很少的状态，等待队列按需交给 ParkingLot 管理。其原文报告锁对象占 `1` 字节，在当时测试中比所比较的 OS [互斥量](#互斥量)小 `64` 倍，微基准中的速度优势最高达到 `180` 倍；应用层面的 JetStream 提升约 `10%`，Speedometer 与页面加载测试约 `5%`。原语的巨大差异并没有等比例变成整个程序的加速，因为程序还在做许多其他工作。这些数值都属于特定实现和测试。[Locking in WebKit](https://webkit.org/blog/6161/locking-in-webkit/)
![PPT 第 11 页](slides/page-015.png)

![PPT 第 11 页](slides/page-016.png)

![PPT 第 11 页](slides/page-017.png)


**[队列自旋闩](#队列自旋闩)（Queue-based Spin Latch）**，如 MCS Locks，组织等待者排队，让它们尽量围绕各自的等待状态等待，减少所有核心反复争抢同一位置。更进一步还有乐观[锁](#锁)耦合（Optimistic Lock Coupling）等树访问技术。这里先保留这些设计方向；后文使用的是明确获取[内部节点](#内部节点)[读闩](#读闩)的乐观蟹行协议，不应仅因名字相近便把不同实现的细节混在一起。

至此，需要分清两个设计层次：[闩](#闩)实现决定一次申请失败后如何等待，数据结构协议决定申请哪个[闩](#闩)、以什么模式申请以及何时释放。只要接口满足协议要求，后面的[哈希表](#哈希表)和 [B+ 树](#B+%20树)都可以搭配不同的底层[闩](#闩)实现。

## 3. [哈希表](#哈希表)：布局不动，就能逐段释放保护

📍 *PPT 第 16–19 页*

### 3.1 一次只占有一个[页](#页)或[槽](#槽)，等待就不容易成环

📍 *PPT 第 16–17 页*

回顾第 [7](../L07/index.md) 讲的线性探测（Linear Probing）：键经过哈希确定起始[槽](#槽)，遇到[冲突](#冲突)后沿规定方向继续检查槽位。先考虑不会在访问过程中扩容的[静态哈希](#静态哈希)表，各[页](#页)和各槽的位置固定。线程从当前槽走到下一个槽时，可以先放开当前槽，再申请下一个槽的[闩](#闩)，因为下一槽的位置不依赖刚刚读过的可变指针。
![PPT 第 16 页](slides/page-029.png)


**[死锁](#死锁)（Deadlock）**是若干[工作者](#工作者)互相等待对方持有的资源，导致它们都无法继续的局面。若每个[工作者](#工作者)至多持有一个[页](#页)或[槽](#槽)的[闩](#闩)，并在申请下一个之前释放当前[闩](#闩)，就不会形成“拿着我的[闩](#闩)，再等你的[闩](#闩)”的循环。统一探测方向让访问规则简单；真正关键的条件还包括持[闩](#闩)方式。仅凭“大家都沿同一方向”不能为任意扩展后的算法证明无[死锁](#死锁)，尤其不能忽略回绕和额外持有的资源。

扩容会打破位置固定的前提。一个简单办法是给表设置 **[全局闩](#全局闩)（Global Latch）**：普通访问先取得全局[读闩](#读闩)，使整张表的布局保持稳定，再按较细粒度的规则访问槽位；扩容者取得全局[写闩](#写闩)，等待当前访问退出后重建布局。这个方案用扩容期间的暂停换取简单的生命周期保护。

[动态哈希](#动态哈希)（Dynamic Hashing），例如第 [7](../L07/index.md) 讲的[可扩展哈希](#可扩展哈希)，还要同步[目录](#目录)、[桶](#桶)指针以及桶的[分裂](#分裂)。它多了一层共享状态，但仍然遵循同一原则：先确定哪些结构变化可能让现有访问失效，再决定这些变化需要排斥哪些访问。

### 3.2 闩粒度决定哪些无关操作会彼此阻塞

📍 *PPT 第 17–19 页*

**[闩粒度](#闩粒度)（Latch Granularity）**是一个[闩](#闩)覆盖的对象范围。范围越大，管理通常越简单，但不相干的访问也更容易被归入同一次互斥。
![PPT 第 17 页](slides/page-030.png)


| 保护粒度 | 一次申请覆盖什么 | 并行性的主要限制 | 主要成本 |
|---|---|---|---|
| 整张表 | 全表内容 | 一个写者会阻挡整张表上的其他访问 | 元数据少，但争用集中 |
| [页](#页)／块 | 一个页中的全部[槽](#槽) | 同页不同槽的读写也可能冲突 | 每页一份[闩](#闩)；扫描同页多个槽只需申请一次 |
| 槽 | 单个键值位置 | 通常只排斥对同一槽的不兼容访问 | 每槽一份[闩](#闩)，探测多个槽要反复申请、释放 |

全表[读写闩](#读写闩)仍允许多个读者共享；把更新放在全表[写闩](#写闩)内，才会把这些更新串行化。[页](#页)[闩](#闩)也同理：同页多个读者可以并行，独占写者才会阻挡同页其他访问。

[槽](#槽)[闩](#闩)能够减少这种额外阻塞，但元数据可能与键值一样贵。若一个键值对和它的[闩](#闩)各占同样多的字节，那么只看这两项，存储就变成原来的两倍。键值大小、访问是否集中在同一[页](#页)、读写比例和核心数共同决定细化粒度是否划算，不存在固定的“槽[闩](#闩)比页[闩](#闩)快多少倍”。对于很小的槽，也可以选单一模式的[自旋闩](#自旋闩)，以减少元数据和判断成本，代价是同槽读者也无法共享。

### 3.4 [页](#页)还在内存中，与页内容可安全访问，是两项保证

📍 *PPT 第 17–19 页*

如果[哈希表](#哈希表)由[缓冲池](#缓冲池)（Buffer Pool，见第 [4](../L04/index.md) 讲）管理，细化到[槽](#槽)的保护还要与页面生命周期配合。**钉住（Pin）**[页](#页)，保证访问期间其缓冲池[帧](#帧)不会被替换；槽[闩](#闩)或页[闩](#闩)则保护页中的内容。仅有 pin，其他线程仍可能修改页内数据；仅有内容[闩](#闩)，也不能自动替代缓冲池约定的生命周期管理。

修改槽位后，还需要把[页](#页)标记为[脏页](#脏页)（Dirty Page），以便[缓冲池](#缓冲池)知道需要写回。脏标记属于另外一项共享元数据，其更新要遵守缓冲池自己的同步规则。不能因为几个读者不关心脏位，就[断言](#断言)脏位的并发更新不需要同步；也不必因此把所有[槽](#槽)操作一律改成持有整页的[写闩](#写闩)。页的驻留、内容访问和脏状态是相关但不同的职责，可以由不同机制协调。

官方 Notes 还给出 **[无闩访问](#无闩访问)（Latch-free Access）**的方向：直接用[原子操作](#原子操作)发布[槽](#槽)内容。在线性探测插入中，可以尝试把某个槽从特殊的 `null` 状态 CAS 成新条目；若其他线程先占用了它，就继续按协议探测。

这个思路把“先占有[闩](#闩)，再写[槽](#槽)”压缩成对槽状态的原子转换。前提是被发布的内容或指向它的指针能以正确的原子方式更新；大[元组](#元组)不会因为调用了 CAS 就整体获得原子性。完整设计仍要处理重复键、删除、扩容和对象回收。这里的无[闩](#闩)是说这条[访问路径](#访问路径)不显式获取[闩](#闩)，并不表示不需要同步协议。

## 4. [B+ 树](#B+%20树)：保护路径，并让结构变化停在安全节点

📍 *PPT 第 20–27 页*

### 4.1 指针仍然有效，查找也可能走错地方

📍 *PPT 第 20–21 页*

回顾第 [8](../L08/index.md)、[9](../L09/index.md) 讲的 [B+ 树](#B+%20树)（B+ Tree）：[内部节点](#内部节点)用[分隔键](#分隔键)（Separator Key）引导查找，[叶节点](#叶节点)保存[索引](#索引)条目；插入可能[分裂](#分裂)节点，删除可能触发合并或[重分配](#重分配)。并发访问由此出现两种危险：多个写者同时改坏一个节点，以及读者使用了结构变化之前的访问决定。

第二种危险更容易被低估。只看课件示例中最右侧的局部结构：
![PPT 第 21 页](slides/page-056.png)


```text
                  D [ 38 | 44 ]
                   /     |     \
          G [35 36]   H [38 41]   I [44  _]
```

`T1` 要删除 `44`。删除后 `I` 变空，需要从 `H` 借一个键恢复占用要求。`T2` 同时查找 `41`，可能遇到以下交错：

| 时刻 | T1：删除 44 | T2：查找 41 |
|---|---|---|
| 1 | 删除 `I` 中的 `44`，尚未[重分配](#重分配)，暂时停下 | — |
| 2 | — | 读到 `D` 中的旧[分隔键](#分隔键) `38、44`，确定应去 `H`；尚未进入 `H` 就停下 |
| 3 | 把 `41` 从 `H` 搬到 `I`，把右侧分隔键由 `44` 改成 `41` | — |
| 4 | 操作结束 | 根据已经作出的决定进入 `H`，发现其中没有 `41`，错误地返回未找到 |

```text
After redistribution:

                  D [ 38 | 41 ]
                   /     |     \
          G [35 36]   H [38  _]   I [41  _]

T2 still follows its old decision: D -> H
```

`41` 从未被删除，`H` 也没有变成无效地址。错误发生在父节点上的路由判断与子节点上的读取属于两个不同的结构状态。若变化还涉及节点回收，后果可能进一步变成访问无效内存。
![PPT 第 21 页](slides/page-064.png)

![PPT 第 21 页](slides/page-065.png)

![PPT 第 21 页](slides/page-066.png)


因此，仅在读每个节点时短暂保护该节点还不够。我们需要保证从父节点确定子节点，到取得对子节点的保护之间，没有让相关结构变化穿过来的空隙。

### 4.2 [闩](#闩)蟹行协议与安全节点

📍 *PPT 第 22–23 页*

**[闩](#闩)蟹行协议（Latch Crabbing，也称 Latch Coupling，[闩耦合](#闩蟹行协议／闩耦合)）**在沿树下降时，先持有父节点的[闩](#闩)，再取得子节点的[闩](#闩)，确认满足释放条件后，才释放祖先的[闩](#闩)。它在两个节点之间短暂重叠保护，把一次移动接成连续的受保护访问。

查找只需要[读闩](#读闩)（Read Latch）。有了子节点的[读闩](#读闩)，线程便能在该节点中继续找路，父节点不必一直被占用。更新则必须多考虑一步：子节点中的变化会不会要求自己回到父节点修改结构？

**[安全节点](#安全节点)（Safe Node）**是对当前操作而言能够吸收变化、不必把结构修改继续传播给父节点的节点。在这里的常规单键更新与[分隔键](#分隔键)约定下，可以用以下条件判断：

| 操作 | 安全条件 | 为什么足以停止向上传播 |
|---|---|---|
| 插入 | 节点未满，能够再接纳一个条目 | [叶节点](#叶节点)可直接插入；[内部节点](#内部节点)可吸收下方[分裂](#分裂)带来的一个新分隔项 |
| 删除 | 节点条目数高于允许的最小值 | 叶节点可直接删除；内部节点可吸收下方合并造成的一个条目减少 |
| 查找 | 不需要按占用量判定 | 查找本身不会造成分裂、合并或[重分配](#重分配) |

用 `n` 表示按节点格式正确计数的当前条目数，`M` 为最大值，`m` 为最小值，则单步插入安全要求 `n + 1 ≤ M`，单步删除安全要求 `n - 1 ≥ m`。课件把后者简称为“多于半满”。[内部节点](#内部节点)的键数与孩子数相差 `1`，[根节点](#根节点)也有特殊规则，因此实际判断应使用该类节点的容量约定，不能对所有节点机械套同一个“半数”。

安全性是相对于操作而言的。一个满节点对插入不安全，却可能对删除安全；一个处在最低占用量的节点则恰好相反。它也不表示下方所有节点都安全。即使下方发生[分裂](#分裂)，只要当前节点能够接住多出来的分隔项，变化就到此为止。

由此得到基本更新规则：沿路径取得[写闩](#写闩)（Write Latch，部分资料记作排他模式 X）；每取得一个节点的[写闩](#写闩)，就判断它能否吸收当前操作可能传上来的变化。若安全，释放此前仍持有的**所有祖先[闩](#闩)**，继续保留当前节点的[闩](#闩)；若不安全，保留祖先保护，继续下降。直到[叶节点](#叶节点)后，执行所需更新。
![PPT 第 23 页](slides/page-068.png)


这套规则提前保留了可能向上传播时需要的保护，避免先改[叶节点](#叶节点)，再拿着叶节点的[闩](#闩)向上追着申请祖先[闩](#闩)。后者会打乱统一的向下获取顺序。

### 4.3 查找 38：父子之间的交接必须有重叠

```text
                         A [20 | _]
                        /          \
                      ...        B [35 | _]
                                /          \
                        C [23 | _]        D [38 | 44]
                        /       \          /    |    \
                E [20 22]  F [23 31]  G [35 36] H [38 41] I [44 _]
```

```text
R(A)
R(B)  -> U(A)
R(D)  -> U(B)
R(H)  -> U(D)

U(H)
```

每次交接都先拿到下一个[闩](#闩)。在 `R(B)` 成功之前，仍由 `R(A)` 保护父节点上的路由；成功之后，`R(B)` 又保护当前所处的节点。这个重叠正好堵住上一节“已经选好指针，但目标节点还没受到保护”的空隙。

### 4.4 删除 38：安全的[内部节点](#内部节点)能截断连锁反应

📍 *PPT 第 25 页*

现在从同一原始状态删除 `38`。示例中每个[叶节点](#叶节点)最多容纳 `2` 个键，最低保留 `1` 个；所画[内部节点](#内部节点)最多有 `2` 个[分隔键](#分隔键)。`B` 只有一个分隔键，若下方合并迫使它再少一个条目，就可能影响根。`D` 有两个分隔键，能够吸收一次减少。
![PPT 第 25 页](slides/page-075.png)

| 步骤 | 本次动作与判断 | 该步完成后仍持有的[写闩](#写闩) |
|---|---|---|
| 1 | 取得 `A` 的[写闩](#写闩)，尚不知道删除会传播多远 | `A` |
| 2 | 取得 `B` 的[写闩](#写闩)；`B` 位于最低占用量，不能保证独自吸收下方合并 | `A、B` |
| 3 | 取得 `D` 的[写闩](#写闩)；即使它少一个分隔项，仍然有效，可以释放祖先 `A、B` | `D` |
| 4 | 取得 `H` 的[写闩](#写闩)；`H = [38, 41]` 删除一个键后仍有一个键，所以释放 `D` | `H` |
| 5 | 删除 `38`，得到 `H = [41]`，随后释放 `H` | 无 |

第 3 步的判断发生时，还没有读到 `H`。这并不妨碍释放 `A` 和 `B`：我们已经证明，无论下方是否需要合并，传到 `D` 的一次条目减少都能被它吸收。因此没有必要继续阻挡整棵树上与当前修改无关的访问。
![PPT 第 25 页](slides/page-077.png)

![PPT 第 25 页](slides/page-080.png)


为什么第 5 步没有把 `D` 中的[分隔键](#分隔键) `38` 改成 `41`？这里沿用示例的范围边界语义：`38` 仍能作为该孩子的有效下界，`38 ≤ key < 44` 的查找仍然正确进入 `H`。删除后，分隔键不一定等于叶中的当前最小键。若某种实现要求它始终精确等于子树最小键，就必须把这种父节点更新需求也纳入安全判断。安全的实质始终是“本次变化是否还需要修改父节点”。

可释放多个祖先[闩](#闩)时，释放次序一般不改变这里的正确性，但会影响并行性。优先释放位置更高的祖先，能够更早放行去往其他子树的[工作者](#工作者)。已经在树内部的[工作者](#工作者)可能另有进展，所以不能说“只要根没释放，所有人都绝对动不了”；准确的收益是尽早解除覆盖范围更广的入口阻塞。

### 4.5 插入 45 与 25：不安全节点决定保留哪一段路径

📍 *PPT 第 26–27 页*

先从原始状态插入 `45`，路径是 `A → B → D → I`。取得 `B` 的[写闩](#写闩)后，发现它尚有空位，能吸收下方可能[上推](#上推)的新分隔项，于是释放 `A`。`D` 已满，所以进入 `D` 后仍要保留 `B`。直到取得[叶节点](#叶节点) `I` 的[写闩](#写闩)，看到 `I = [44]` 可以直接变成 `[44, 45]`，才确定不需要修改 `D`，于是把 `B、D` 一并释放，只在 `I` 上完成插入。

这解释了一个看似多余的动作：途中暂时保留 `B`，并不是已经决定要修改它；当时还没有证据证明下方不会向它传播变化。进入安全[叶节点](#叶节点)后，这种可能性才被排除。
![PPT 第 26 页](slides/page-087.png)


再从原始状态插入 `25`，路径变成 `A → B → C → F`。`B` 与 `C` 都有空余分隔项，而 `F = [23, 31]` 已经满了。此时真正需要修改的是 `F` 和其父节点 `C`。

| 步骤 | 本次动作与判断 | 保留的既有节点[写闩](#写闩) |
|---|---|---|
| 1 | 取得 `A`，随后取得 `B`；`B` 安全，释放 `A` | `B` |
| 2 | 取得 `C`；`C` 安全，释放 `B` | `C` |
| 3 | 取得 `F`；`F` 已满，将发生[分裂](#分裂)，保留父节点 `C` | `C、F` |
| 4 | 分配新[叶节点](#叶节点) `J`，把有序键分配为 `F = [23, 25]`、`J = [31]` | `C、F`，新节点发布也须受保护 |
| 5 | 给 `C` 增加[分隔键](#分隔键) `31` 和指向 `J` 的指针，完成需要的链路更新 | 相关修改完成前继续保护涉及的节点 |
| 6 | 操作完成，释放所持保护 | 无 |

只画发生变化的局部结构：

```text
Before insertion:

             C [23 | _]
              /       \
       E [20 22]     F [23 31]

After inserting 25 and splitting F:

                  C [23 | 31]
                 /     |     \
          E [20 22] F [23 25] J [31 _]
```

`C` 能接纳新[分隔键](#分隔键) `31`，所以这次[分裂](#分裂)不必影响 `B`。第 2 步释放 `B` 正是建立在这个事实之上。我们因此得到一个很有用的理解：保留下来的祖先[闩](#闩)，为更新的最远传播范围划定了一条边界；一个[安全节点](#安全节点)能够让更高层脱离本次更新。

![PPT 第 27 页](slides/page-093.png)

![PPT 第 27 页](slides/page-096.png)


[叶节点](#叶节点)之间还有[兄弟指针](#兄弟指针)（Sibling Pointer）。若[分裂](#分裂)后要把新叶 `J` 接在 `F` 与原右兄弟 `G` 之间，双向链表还可能需要修改 `G` 的回指。这要求对实际修改的 `G` 取得相应保护，不能只因持有 `C` 的[写闩](#写闩)，就认为所有孩子和兄弟都已被自己独占：其他线程可能早已越过祖先，或者从叶链横向到达。如何获取横向的[闩](#闩)，是第 6 节要补上的规则。

## 5. 乐观蟹行：让常见更新绕开根写闩的争用

📍 *PPT 第 28–32 页*

### 5.1 每次都先独占根，代价集中在所有路径的交汇处

📍 *PPT 第 28–30 页*

基本[闩](#闩)蟹行协议（Latch Crabbing）已经能提前释放[安全节点](#安全节点)之上的保护，但所有插入和删除仍从根的[写闩](#写闩)开始。两个[工作者](#工作者)即使分别修改树的最左侧与最右侧，也得先在同一个入口排队。根[写闩](#写闩)不一定贯穿整个操作，却仍使入口成为高并发时的瓶颈。

多数更新只改变一个[叶节点](#叶节点)，并不引起[分裂](#分裂)或合并。基本协议却为可能发生的结构修改，预先在整条下降路径上申请[写闩](#写闩)。若这种较少见的情况可以被识别并重试，就有机会降低常见路径的同步成本。
![PPT 第 29 页](slides/page-098.png)


**[乐观闩蟹行协议](#乐观闩蟹行协议)（Optimistic Latch Crabbing）**先假定更新只需要修改目标[叶节点](#叶节点)：[内部节点](#内部节点)像查找一样使用[读闩](#读闩)，到了叶节点取得[写闩](#写闩)，再检查本次更新是否安全。假设成立就完成更新；不成立就释放本次尝试持有的[闩](#闩)，从根重新执行基本[写闩](#写闩)协议。相对而言，后者也称为悲观协议（Pessimistic Protocol），因为它事先保留了结构变化所需的保护。

“乐观”体现在先走成本较低的常见路径；正确性依靠实际检查和失败后的退路。[叶节点](#叶节点)是否安全，必须在取得其[写闩](#写闩)后判断，否则另一个写者可能在检查结束后、修改开始前改变占用情况。

### 5.2 到叶前仍读共享，到叶时直接取得写闩

📍 *PPT 第 30–32 页*

以删除 `38` 为例，内部路径仍是 `A → B → D`，[叶节点](#叶节点)是 `H`。在下降过程中按父子交接规则释放旧[读闩](#读闩)；到 `D` 后，持有 `D` 的[读闩](#读闩)，直接申请 `H` 的[写闩](#写闩)。
![PPT 第 31 页](slides/page-100.png)

![PPT 第 31 页](slides/page-101.png)

![PPT 第 31 页](slides/page-102.png)


```text
R(A)
R(B) -> U(A)
R(D) -> U(B)
W(H) -> inspect H while still protected

H = [38, 41]: deletion is safe
U(D)
delete 38 from H
U(H)
```

这里不要求先拿 `H` 的[读闩](#读闩)再升级。父节点中的节点类型或层级信息足以帮助判断下一层是叶层，因此可以在进入目标叶时就申请所需的写模式。拿到 `W(H)` 后，确认删除一个键不会引起合并或[重分配](#重分配)，便可释放 `R(D)`，完成更新。
![PPT 第 31 页](slides/page-103.png)

![PPT 第 31 页](slides/page-104.png)

![PPT 第 31 页](slides/page-105.png)

![PPT 第 31 页](slides/page-106.png)


查找操作继续使用原有的全程[读闩](#读闩)协议。插入 `25` 则展示了乐观假设失败的情况：取得 `F` 的[写闩](#写闩)后，发现 `F = [23, 31]` 已满。它需要[分裂](#分裂)，并修改父节点 `C`；当前只有或曾经有过 `C` 的[读闩](#读闩)，不能直接完成这种结构变化。

因此这次尝试在真正插入之前就退出，释放仍持有的叶[写闩](#写闩)和祖先[读闩](#读闩)，然后从根按基本协议重新下降。第二次到达 `F` 时，所保留的 `C` [写闩](#写闩)能够支持第 4.5 节的[分裂](#分裂)。

如果[分裂](#分裂)和合并很少，绝大部分更新只在最后的[叶节点](#叶节点)互斥，不再用根[写闩](#写闩)阻挡彼此。若某种[工作负载](#工作负载)频繁触发结构变化，第一次下降就会经常白做，乐观策略的优势也会减弱。这项优化的根据是操作分布，而不是“乐观”这个名字本身。

### 5.3 为何不原地升级，或者从上次经过的节点继续

📍 *PPT 第 29–32 页*

**[闩升级](#闩升级)（Latch Upgrade）**是把已经持有的读模式转换为写模式。它看起来可以省[去重](#去重)走路径，但比重新调用一次[写闩](#写闩)申请复杂。

首先，共享[读闩](#读闩)可能有多个持有者。若两个读者都保留自己的[读闩](#读闩)，等待另一个退出后再升级成[写闩](#写闩)，就会彼此等待。安全的升级实现必须另有规则，例如只允许一个升级者，或升级失败后释放并重试；不能假定任意[读写闩](#读写闩)都支持原子升级。

其次，[叶节点](#叶节点)需要[分裂](#分裂)时，仅升级叶节点自身没有帮助，父节点也要被写保护。如果线程已经释放父节点的[闩](#闩)，再一边持有叶[闩](#闩)、一边向上申请父[写闩](#写闩)，就可能与正在向下访问的线程形成反向依赖。即使保留了某个祖先的[读闩](#读闩)，也仍须处理升级竞争以及可能进一步向上传播的变化。

最后，上一次走过的路径不等于当前仍有效的路径。已经释放保护的 `B` 或 `C` 可能被别的线程修改、[分裂](#分裂)或重新挂接。仅仅记住它们的地址，不能证明自己仍能安全地从那里继续操作；若要局部重启，就需要额外的稳定性保证或重新验证。

一些[闩](#闩)和树算法确实能支持更精细的升级与局部重试，官方 Notes 也提到这条优化方向。但它们必须为省下的一次遍历付出更多状态管理与证明成本。Andy 的判断是：“很多时候，最简单的办法也是最容易实现、或者最好的办法。”[^simple] 在这里，从根重试的价值很具体：把第二次操作重新放回一个已有正确性依据的协议。

## 6. 沿[叶节点](#叶节点)横向扫描，必须给失败留出出口

📍 *PPT 第 33–37 页*

### 6.1 向下获取的顺序，为什么不能直接覆盖横向移动

📍 *PPT 第 33–34 页*

如果获取[闩](#闩)时只沿父到子的方向向下，新申请的节点总比当前节点更深，那么这类依赖就无法沿树高回到起点。基本协议即使需要把修改向上传播，使用的也是下降时已经保留的祖先[写闩](#写闩)，并没有拿着孩子[闩](#闩)重新向上申请祖先[闩](#闩)。

范围扫描（Range Scan，见第 [8](../L08/index.md)、[9](../L09/index.md) 讲）还要沿[叶节点](#叶节点)的[兄弟指针](#兄弟指针)横向移动。为支持两个方向的扫描，考虑以下小树：

```text
             A [3]
             /   \
        B [1 2] <-> C [3 4]
```

`T1` 查找所有 `< 4` 的键，可以先到 `C`，读出满足条件的 `3`，再向左到 `B`，读取 `2、1`。从 `C` 到 `B` 时仍需交接保护：保持 `C` 的[读闩](#读闩)，先取得 `B` 的[读闩](#读闩)，再释放 `C`。若先释放 `C` 才按旧指针访问 `B`，期间发生的合并或链路变化可能使原访问依据失效。
![PPT 第 34 页](slides/page-110.png)

![PPT 第 34 页](slides/page-112.png)

![PPT 第 34 页](slides/page-113.png)


保持当前节点保护，也约束了修改者能做什么。若一次结构变化需要改写当前节点中的[兄弟指针](#兄弟指针)，修改者就必须先取得该节点的[写闩](#写闩)；它不能越过仍持有[读闩](#读闩)的扫描者，悄悄完成[冲突](#冲突)的链路修改。这正是保护交接能够成立的基础，[页](#页)本身的生命周期则仍需由 pin 等配套机制保证。
![PPT 第 34 页](slides/page-111.png)


现在，依赖关系不再只指向更深的一层。一个线程可能从左向右申请[闩](#闩)，另一个从右向左申请，统一的向下顺序已不足以排除循环。

### 6.2 两个读者可以交错，读写[冲突](#冲突)却不等于已经死锁

📍 *PPT 第 35–36 页*

让 `T1` 查找 `< 4`，从 `C` 向 `B` 扫描；让 `T2` 查找 `> 1`，从 `B` 向 `C` 扫描。两者都使用[读闩](#读闩)（Read Latch），可以短暂同时持有 `B` 与 `C` 的[读闩](#读闩)，完成交接后各自释放旧节点。访问方向相反，本身并不造成[冲突](#冲突)。

再把 `T1` 改成删除 `4`，`T2` 仍查找所有 `> 1` 的键：
![PPT 第 36 页](slides/page-120.png)


| 时刻 | T1：删除 4 | T2：扫描 > 1 |
|---|---|---|
| 1 | 沿[读闩](#读闩)路径进入树，取得 `C` 的[写闩](#写闩) | 沿[读闩](#读闩)路径进入树，取得 `B` 的[读闩](#读闩) |
| 2 | 持有 `W(C)`，准备修改 `C` | 在 `B` 读到 `2`，准备向右移动 |
| 3 | 仍持有 `W(C)` | 申请 `R(C)` 失败，因为[写闩](#写闩)排斥读者；此时仍持有 `R(B)` |

这时只有 `T2` 在等待 `T1`。在这个具体例子中，删除 `4` 后 `C` 仍有 `3`，无需合并，也不需要取得 `B` 的[闩](#闩)。`T1` 可以自行完成并释放 `C`，因此**此刻没有形成[死锁](#死锁)**。
![PPT 第 36 页](slides/page-121.png)


[死锁](#死锁)风险出现在更一般的结构修改中：若持有 `C` [写闩](#写闩)的[工作者](#工作者)还需要取得 `B` 的[写闩](#写闩)，而扫描者拿着 `B` 的[读闩](#读闩)等 `C`，等待关系就形成了环。这是对上例的扩展情形，不能把它冒充为删除 `4` 的原始执行过程。

难点在于，`T2` 通常看不到 `T1` 的完整计划。它知道目标[闩](#闩)不可用，却不知道持有者接下来是否要访问自己占有的节点。因此，协议必须给横向获取失败规定统一的处理办法，不能要求每个等待者推测另一个线程的下一步。
![PPT 第 36 页](slides/page-122.png)


### 6.3 无等待模式：结束当前尝试，释放后重试

📍 *PPT 第 36–37 页*

**[无等待模式](#无等待模式)（No-wait Mode）**让[工作者](#工作者)尝试取得兄弟节点的[闩](#闩)；若不能立即取得，就返回失败，由操作代码释放本次持有的保护并重试，而不是拿着已有[闩](#闩)无限等待。它需要类似“尝试获取并返回成功与否”的接口，也需要每个调用者真正处理失败路径。

对上面的 `T2` 而言，获取 `C` 失败后，可以结束本次扫描尝试并释放 `B`。这不仅让自己退出等待，也让潜在需要 `B` 的修改者继续运行。下一次重新定位后，原来[冲突](#冲突)的操作可能已经完成。本次读取产生的临时结果也要按查询执行层的约定清理或续接，避免重试后重复输出已经返回的条目。
![PPT 第 37 页](slides/page-125.png)


```text
T2 holds R(B)
    |
    +-- try R(C) succeeds --> release B --> read C
    |
    +-- try R(C) fails ----> end this attempt --> release B --> retry
```

这是一种内部操作重试，通常对最终用户和应用透明。“结束当前尝试”不表示杀死 OS 线程，也不必等同于让整个用户[事务](#事务)中止。[工作者](#工作者)继续存在，只是放弃这次未能完成的内部操作路径。

有的实现会先作有界的短暂等待，再执行同样的清理和重试。这样可以减少某些过早退出，但必须有明确的退出路径；把“也许很快就能拿到”当成无限等待的理由，会重新引入无法解除的循环依赖。

另外两种看似直接的处理方式都有隐藏成本。跳过被占用的[叶节点](#叶节点)，会漏掉可能满足条件的键；若准备之后补读，就要重新定位、记录遗漏区间并维护结果语义。强行终止持[闩](#闩)者，则需要知道它是谁、持有哪些其他[闩](#闩)、已经修改了什么，以及如何恢复这些修改。当前的轻量[闩](#闩)并没有提供这些全局信息，直接终止线程还可能把数据结构留在半更新状态。

所以失败处理最好从自己掌握的信息出发：自己持有什么、自己改过什么，以及自己能安全撤回到哪里。第 7 节的[写集合](#写集合)正是为此准备的。

### 6.4 无死锁并不保证每个人都能及时完成

📍 *PPT 第 36–37 页*

无等待重试消除了某些持续的等待环，却仍可能产生[饥饿](#饥饿)（Starvation）。同一个扫描者可能每次接近目标叶时都碰上写者，然后一次次退出；其他[工作者](#工作者)持续完成操作，它却始终不能完成。

可以记录重试次数，调整再次尝试的时机。**[退避](#退避)（Backoff）**是在失败后延迟或调整重试节奏，减少一批[工作者](#工作者)总在同一时刻重新[冲突](#冲突)。若局部策略长期不能使某个请求前进，更高层的调度器可以暂时限制新访问，为它创造完成机会。官方 Notes 特别指出，这种帮助可以放在系统调度层，不必塞进每个数据结构的基本实现。

两种等待需要区分：释放已有[闩](#闩)后，稍晚再试；持有已有[闩](#闩)时，继续等另一个[闩](#闩)。前者不会继续占住原来的依赖链，后者则必须受到更严格的限制。“多睡一会儿”本身不能证明协议安全，也不能保证公平。

如果所有[工作者](#工作者)都要独占修改同一个键或同一个节点，这部分工作本来就需要相互排斥。细粒度保护可以让其他位置的访问继续运行，但无法把对同一份可变状态的[冲突](#冲突)修改自动变成互不冲突的工作。

最后，范围扫描期间究竟允许看到哪些插入和删除，仍属于[逻辑正确性](#逻辑正确性)（Logical Correctness）。读到一份结构有效的结果，并不自动意味着读到了同一时刻的快照。第 [17](../L17/index.md)、[18](../L18/index.md)、[19](../L19/index.md)、[20](../L20/index.md) 讲会提供[事务](#事务)层面的规则，补足这里尚未定义的语义。

## 7. 写到一半需要退出，怎样把结构交还给别人

📍 *PPT 第 38 页*

### 7.1 工作期间保留写集合与必要的写闩

📍 *PPT 第 38 页*

纯读取尝试失败，通常只需清理本地读取状态并释放[闩](#闩)。修改则可能已经发生：某个[工作者](#工作者)写过一个[叶节点](#叶节点)，继续获取另一个节点的[写闩](#写闩)时失败。如果它直接退出，其他[工作者](#工作者)就会看到本次操作的一部分结果。

**[写集合](#写集合)（Write-set）**记录一个[工作者](#工作者)在当前内部操作中做出的修改。这里可以把它理解为[工作者](#工作者)私有的修改清单，其中有涉及的节点标识，以及插入、删除了哪些键；实际撤销删除还必须保留足以恢复相应条目的信息。它的作用范围是当前操作，不能直接当成后来[事务](#事务)章节中的完整[事务](#事务)状态。

在这里采用的失败处理模型中，对已经修改过、可能还要撤销的节点，[工作者](#工作者)继续持有[写闩](#写闩)（Write Latch），直到整个内部操作成功，或失败清理完成。这样其他线程便不能在这段时间读走尚未确定保留的修改。

```text
Worker-private write-set:

    node identifier -> inserted entries / deleted entries

Success:
    finish the operation -> discard temporary undo state -> release latches

Failure to acquire a required latch:
    undo recorded modifications while protected -> release all latches -> retry
```

这里的次序有实际意义。若先释放[写闩](#写闩)，再撤销修改，别的[工作者](#工作者)可能已经读到了部分结果，甚至在其基础上又作了修改。失败清理必须在必要保护仍然存在时完成。

这与基本蟹行协议的“尽早释放祖先[闩](#闩)”并不[冲突](#冲突)。沿途某个[安全节点](#安全节点)使我们确定不需要修改更高祖先时，可以释放那些祖先；已经改过而尚未完成操作的节点，则承担着不同的职责，需要继续遮住未完成的结果。决定是否放[闩](#闩)，要看接下来是否还依赖它保护的状态。

### 7.2 撤销键值变化，不必逐字节恢复原树形

📍 *PPT 第 38 页*

如果插入触发了[分裂](#分裂)，之后操作又需要撤销，把新键移除相对容易，把整棵树恢复成分裂之前的形状可能贵得多：要移动条目、更新父节点、修复[兄弟指针](#兄弟指针)，还可能与其他结构维护互相影响。

因此，有些设计在撤销条目修改后，允许保留已经完成且仍然有效的结构变化，而不强行反向执行每一次[分裂](#分裂)。这与第 [8](../L08/index.md)、[9](../L09/index.md) 讲中延迟合并、适当放宽占用要求的思路相通：维护紧凑程度与维护查找正确性可以有不同的时机。

这种放宽有明确边界。键的顺序、可达性、父子路由和兄弟链必须保持一致，不能留下悬空指针或只有一半完成的链接。某些节点暂时低于通常的占用目标，需要由该设计的规则允许并在后续维护；这也不表示可以随意让 [B+ 树](#B+%20树)的[叶节点](#叶节点)落在不同高度。

更完整的结构修改与回收算法会超出这里的范围。当前需要掌握的是：成功路径和失败路径都必须把数据结构交还为其他[工作者](#工作者)能安全使用的状态。只证明“所有[闩](#闩)都能取得时算法正确”，还没有证明一个并发数据结构正确。

## 小结

📍 *PPT 第 39–40 页*

[索引](#索引)并发访问的困难，来自一个操作可能看到另一个操作尚未完成的中间状态。[闩](#闩)为局部访问提供互斥，协议把这些局部保护连接成完整过程：[静态哈希](#静态哈希)表利用稳定布局逐段前进，[B+ 树](#B+%20树)通过父子[闩](#闩)的交接保护路径，再利用[安全节点](#安全节点)截断结构变化的传播范围。乐观蟹行把多数只修改叶节点的操作放到较轻的路径上，将[分裂](#分裂)、合并交给重试后的保守协议。

横向扫描使等待关系超出树的向下顺序，无等待获取与失败清理因此成为协议的一部分。读写兼容决定谁可以同时进入，重试与调度决定谁能继续前进，[写集合](#写集合)与必要的持[闩](#闩)范围保证失败时也能恢复有效状态。这些思想同样适用于其他共享数据结构；第 [17](../L17/index.md)、[18](../L18/index.md)、[19](../L19/index.md)、[20](../L20/index.md) 讲还会在[事务](#事务)层面重新讨论等待、乐观执行与回滚，但保护对象和正确性标准会有所不同。

**Deadlock**：工作者互相等待对方的资源，形成无法前进的环。（本讲首次出现：3.1；引入于：本讲）

### 全局闩

**Global Latch**：覆盖整个数据结构的闩，可用于协调布局变化。（本讲首次出现：3.1；引入于：本讲）

### 静态哈希

**Static Hashing**：槽数在分配时固定，装满后必须整体重建的哈希方案。（本讲首次出现：3.1；引入于：第 7 讲）

### 动态哈希

**Dynamic Hashing**：能按需增量扩缩容、无需整体重建的哈希方案。（本讲首次出现：3.1；引入于：第 7 讲）

### 可扩展哈希

**Extendible Hashing**：桶满时分裂桶、必要时翻倍目录的动态哈希方案。（本讲首次出现：3.1；引入于：第 7 讲）

### 目录

**Directory**：可扩展哈希中按哈希值前缀索引、指向桶的指针数组。（本讲首次出现：3.1；引入于：第 7 讲）

### 桶

**Bucket**：可容纳多个键值对的存储单元，通常是一页。（本讲首次出现：3.1；引入于：第 7 讲）

### 闩粒度

**Latch Granularity**：一个闩所保护的对象范围，如全表、页或槽。（本讲首次出现：3.2；引入于：本讲）

### 无闩访问

**Latch-free Access**：不显式获取闩，而通过原子操作等机制协调访问。（本讲首次出现：3.4；引入于：本讲）

### 帧

**Frame**：缓冲池中能放一页的位置。（本讲首次出现：3.4；引入于：第 3 讲）

### 脏页

**Dirty Page**：标记页在内存中被改过；这样的页淘汰前必须写回。（本讲首次出现：3.4；引入于：第 4 讲）

### 断言

**Assertion**：以任意 SQL 查询为检查条件的全局约束。（本讲首次出现：3.4；引入于：第 1 讲）

### 闩蟹行协议／闩耦合

**Latch Crabbing / Latch Coupling**：先保护子节点，再按安全条件释放祖先保护。（本讲首次出现：4.2；引入于：本讲）

### 安全节点

**Safe Node**：能吸收当前操作的变化，不必继续修改父节点。（本讲首次出现：4.2；引入于：本讲）

### 根节点

**Root Node**：树的查找入口，占用下限有特殊规则。（本讲首次出现：4.2；引入于：第 8 讲）

### 上推

**Push Up**：把内部节点的中间分隔键移到父层。（本讲首次出现：4.5；引入于：第 8 讲）

### 兄弟指针

**Sibling Pointer**：连接同层相邻节点，支持叶扫描及结构维护。（本讲首次出现：4.5；引入于：第 8 讲）

### 乐观闩蟹行协议

**Optimistic Latch Crabbing**：内部节点取读闩、叶节点取写闩，叶不安全则按基本协议重试。（本讲首次出现：5.1；引入于：本讲）

### 工作负载

**Workload**：一个应用发给数据库的查询的整体特征。（本讲首次出现：5.2；引入于：第 1 讲）

### 闩升级

**Latch Upgrade**：将已经持有的读模式转换为写模式。（本讲首次出现：5.3；引入于：本讲）

### 去重

**Deduplication**：重复键只存一份，再关联多个记录位置。（本讲首次出现：5.3；引入于：第 8 讲）

### 无等待模式

**No-wait Mode**：获取失败立即返回，由操作代码清理并重试。（本讲首次出现：6.3；引入于：本讲）

### 退避

**Backoff**：在失败后调整重试时机，降低反复冲突。（本讲首次出现：6.4；引入于：本讲）

### 写集合

**Write-set**：工作者为当前操作保留的修改记录，支持失败清理。（本讲首次出现：7.1；引入于：本讲）

[^simple]: 原话：“Oftentimes, the simplest thing is the easiest thing to do or the best thing to do.” 来自关于闩升级与局部重启的连续发言。
